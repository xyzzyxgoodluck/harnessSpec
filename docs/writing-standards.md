# 写作标准（Docs 与 AGENTS.md 的编写要求）

> 适用范围：编写本仓库任何**类型规范文档**（`<类型>/AGENTS.md`、`<类型>/docs/*`）或**根 docs/** 时都必须遵守。
> 配套：类型结构与流程见 `authoring-types.md`；固定组成部分见 `fixed-docs.md`；变更登记见 `changelog.md`。

## 1. 写作基本原则

1. **简洁、可执行**：多用命令块、表格、清单，少写散文。**类型模板版（地图式）目标 ≤120 行、典型 80–140 行**——它是会被复制到真实项目根的地图，只放不可协商项、入口与命令，细则一律指向 `docs/`（本仓库 `springboot/AGENTS.md` 即此形态）；**真实项目版**（填完占位符、并入项目特有内容后）典型 100–250 行，上限约 300 行。单文件不宜超过 400 行，超长应拆 `docs/` 或「examples/」。
2. **命令必须真实可验证**：只写确认能跑通的命令。模板命令须为该技术栈标准命令并经核实；复制到真实项目后必须逐条实际执行验证一遍。
3. **高频操作置顶**：构建 → 运行 → 测试放在前 1/3；架构、禁忌等参考性内容放后。
4. **确定而非模糊**：不写"建议运行测试"；写成"提交前必须执行 {{cmd}}，失败不得提交"。
5. **单一事实来源**：版本号、端口、路径指向真实配置文件或引用其准确值，不另起炉灶维护会过期的副本。
6. **只写稳定且必要的信息**：架构决策、目录约定、命令、坑；不写源码注释复制品、长篇教程、路线图式愿望。
7. **明确"禁区"**：生成代码目录、密钥文件、需手签的锁文件等，写明"不要改/不要提交"及原因。
8. **让失败可预期**：列出常见失败症状与规避，减少代理反复试错。
9. **随代码同步更新**：真实项目中改命令/结构须同提交更新 AGENTS.md（本仓库的类型文件同理：框架演进即修订）。
10. **为最小上下文服务**：每句都要有信息量；删掉"读起来舒服但没用"的内容。

## 2. 命令与路径书写规范

1. **标注执行目录**：默认"项目根"；否则注释标明，如 `# 在 packages/core 下执行`。
2. **一个动作一条命令**：避免一长串 `&&`；确需串联控制在 2–3 个。
3. **统一包/依赖管理器**：同一真实仓库只允许一种，并在第 1 章声明（类型模板中注明该类型最常用的管理器与备选）。
4. **写明平台差异**：Windows 与 macOS/Linux 不同（如 `venv\Scripts\activate` vs `venv/bin/activate`）须分别给出或统一跨平台入口（`./mvnw`、`pnpm`、`make`）。
5. **占位符与密钥**：可变值用 `<...>` 或 `{{...}}`；**永不**出现真实密钥/token/内网地址。
6. **给出可预期结果**：需要等待、有产物路径/端口时一句话说明，避免把"正在启动"误判为卡死。
7. **禁止编造**：未核实的命令宁可不写。
8. **树形描述用纯缩进**：目录/结构描述使用缩进 + 内联注释（ASCII 安全），**禁用** `├──/└──/│` 等制表符画线字符。
9. **环境准备不进指令文档**：安装 SDK/Docker、手工起中间件、下载耗时等人工 onboarding 细节不写入 AGENTS.md——归真实项目 README/部署文档；AGENTS 只留可执行命令与版本约束。

## 3. 常见反例（✗ → ✓）

| ✗ 反例 | 问题 | ✓ 修正 |
| --- | --- | --- |
| `运行测试` | 无命令、无目录 | `pnpm test`（在项目根执行） |
| `代码应该保持整洁，请遵循良好实践` | 模糊空话 | 提交前必须通过 `pnpm lint`；格式化统一 `pnpm format` |
| 整段粘贴源码注释/README | 双份维护必过期 | 一句指向：`详见 docs/architecture.md` |
| `npm install`（实际用 pnpm） | 命令不真实 | `pnpm install`，第 1 章声明管理器 |
| 列出完整目录树 | 噪音大易过期 | 只列**顶层职责表/职责树** |
| `不要修改 dist/`（无原因） | 无原因则必违反 | `dist/ 由 CI 重新生成；手改会被覆盖且合并必冲突` |
| 模板里写死具体项目名/端口 | 无法复用 | 项目特有值一律 `{{占位符}}` |
| 正文写"将来会支持 X" | 愿望混入事实 | 删除；实现后由修订流程写入 |
| "若有 docs/…"式条件句 | 确定性失效 | 触发器式表述：条件一旦满足**必须**建立并维护 |
| 团队规则写进工具配置但只打印警告 | 假绿：门禁"0 违规"其实没拦任何东西 | 让规则真的拦构建（如 Checkstyle `<violationSeverity>warning</violationSeverity>` 或把 severity 设为 error），并用"故意违规即红"验证一次（口径见 `fixed-docs.md` §6） |
| 只在 `compile` 上验证过的质量门命令 | 命令真实性未证 | 命令必须整条真跑一次（`clean verify`），并在类型 README 记下原始输出与日期（口径见 `fixed-docs.md` §6） |

> 历史与变更登记统一在 `changelog.md`。
